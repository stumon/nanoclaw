## 第一部分：AI Agent 

### 1. Agent 核心架构

**Q: Agent 的基本架构由哪些核心组件构成？**

Agent = LLM + 规划(Planning) + 记忆(Memory) + 工具(Tool Use)

四大核心组件：
- **LLM（大语言模型）**：系统大脑，负责理解任务和决策判断
- **规划模块 (Planning)**：将复杂目标拆解成可执行的步骤，包括任务分解、推理链、反思修正
- **记忆系统 (Memory)**：短期记忆（当前对话上下文/Context Window）+ 长期记忆（向量数据库存储跨会话知识）
- **工具系统 (Tools)**：与外部世界交互的入口，包括搜索引擎、API调用、代码执行、数据库查询等

**Q: Agent 和传统 LLM Chain 的区别是什么？**

- **Chain** 是"固定剧本"的线性工作流，步骤预先定义，按顺序执行
- **Agent** 具备"自主意识"，通过推理循环根据目标自发判断下一步动作，能灵活应对复杂不确定任务
- 关键区别：Agent 有决策循环（观察->思考->行动->观察），Chain 没有

**Q: 工作流 (Workflow) 和自主 Agent 各自适用什么场景？**

- **工作流**：预定义路径、高可靠性、结果可预期，适合标准化、重复性任务（如数据处理流水线）
- **自主 Agent**：动态决策、灵活适应，适合复杂、开放域、不确定性高的任务（如自主研究、多步推理问题）

### 2. ReAct 框架

**Q: 介绍一下 ReAct 框架的核心机制？**

ReAct = Reasoning + Acting，核心机制是循环迭代：

```
思考(Thought) -> 行动(Action) -> 观察(Observation) -> 思考 -> ... -> 最终回答
```

- 每步推理可以与外部世界交互，用真实数据修正推理方向
- 关键区别于纯 CoT（链式推理）：CoT 只在模型内部推理，ReAct 每步可以调用工具获取真实信息

**Q: ReAct 如何解决循环和死锁问题？**

- 设置最大迭代次数（如 10 次）
- 超时熔断机制
- 在 prompt 中加入自检指令，让模型判断是否陷入循环
- 引入状态机管理，明确终止条件

### 3. Function Calling 与 MCP

**Q: Function Calling 的工作原理是什么？**

- 模型根据用户输入和工具描述，判断是否需要调用工具
- 输出结构化的 JSON 请求（函数名 + 参数），而非直接生成自然语言
- 外部程序执行函数后，将结果返回给模型继续推理
- 核心：自然语言 -> 结构化参数映射

**Q: MCP（Model Context Protocol）和 Function Calling 的区别？**

| 维度 | Function Calling | MCP |
|------|-----------------|-----|
| 定义方式 | 每个应用自己定义 | 统一协议标准 |
| 工具发现 | 静态配置，启动时确定 | 支持动态发现 |
| 生态复用 | 难以跨应用复用 | 一次开发，处处可用 |
| 跨模型 | 通常绑定特定模型 | 开放标准，多模型支持 |
| 本质 | 模型级别功能 | 系统级别通信协议 |

MCP 是 Function Calling 的标准化演进方向，被称为 AI 的 "USB-C 接口"。

**Q: Prompt、Function Call、Skill、MCP 的层级关系是什么？**

- **交互层**：Prompt（指令 "要什么"）
- **应用层**：Agent（规划与决策的大脑）
- **模型能力层**：Function Calling（执行 "怎么做"）
- **应用/产品层**：Skill（把相关工具+Prompt+工作流打包成能力模块）
- **基础设施层**：MCP（标准化接口协议）

### 4. RAG（检索增强生成）

**Q: 介绍 RAG 的完整工作流程？**

1. **问题改写 (Query Rewriting)**：优化用户原始问题，提升检索命中率
2. **向量检索 (Retrieval)**：将问题 Embedding 化，在向量数据库中检索相似文档
3. **重排序 (Reranking)**：对检索结果进行精排，提升相关性
4. **上下文注入 (Context Injection)**：将检索到的文档拼接到 prompt 中
5. **LLM 生成 (Generation)**：模型基于上下文生成答案
6. **引用标注 (Citation)**：标记答案中引用了哪些文档

**Q: RAG 相比微调的优劣势？**

RAG 优势：
- 知识实时更新，无需重新训练
- 成本低，只需维护向量数据库
- 答案可追溯验证（有明确来源）
- 适合知识密集型、时效性强的任务

微调优势：
- 知识融入模型内部，推理时无需检索
- 风格和能力的深度定制
- 适合需要改变模型行为模式的场景

**Q: 文档分块有哪些策略？**

- **固定长度分块**：简单快速，但可能切断语义
- **语义分块**：按段落/句子边界切分，保持语义完整，复杂度高
- **滑动窗口分块**：重叠切分（如 512 token 窗口，128 token 重叠），避免边界信息丢失
- **递归分块**：先按大标题切，再按段落切，层层细化

**Q: 向量数据库怎么选型？**

- **FAISS**：GPU 加速，毫秒级响应，适合研究原型和单机大规模检索
- **Milvus**：云原生架构，支持 100B+ 向量，生产环境首选
- **Pinecone**：完全托管零运维，但成本较高，适合快速上线
- **Weaviate**：支持混合检索（向量+BM25），适合全文搜索+语义搜索混合场景

**Q: RAG 工程化中如何做混合检索？**

- 稠密向量检索（Embedding）负责语义相似
- 稀疏向量检索（BM25）负责关键词匹配
- 使用 RRF（Reciprocal Rank Fusion）算法融合两路结果
- 双塔模型粗排 + 单塔模型精排

### 5. 记忆系统设计

**Q: Agent 的记忆系统如何设计？**

- **短期记忆**：当前会话上下文（Context Window），窗口溢出时需摘要压缩或截断
- **长期记忆**：通过向量数据库存储跨会话知识，需质量校验防止记忆污染
- **工作记忆**：当前任务的中间状态和临时数据
- 配合策略：检索相关历史经验注入上下文，短期负责连贯推理，长期负责知识积累

**Q: 如何处理 Context Window 溢出？**

- 滑动窗口截断：保留最近 N 轮对话
- 摘要压缩：定期将历史对话压缩为摘要
- 层级记忆：热数据在 context 中，温数据在缓存中，冷数据在向量库中
- 2026 新趋势：利用长文本模型（100K+ token）处理超长历史

### 6. 多 Agent 协作

**Q: 多 Agent 系统有哪些协作模式？**

1. **中心化模式 (Supervisor/Boss-Worker)**：主管 Agent 负责任务拆解和结果汇总，子 Agent 执行具体任务
2. **流水线模式 (Pipeline)**：前一个 Agent 的输出作为下一个的输入，适合有明确流程的任务
3. **去中心化消息传递**：共享消息总线，Agent 监听相关消息，平等协作
4. **民主协作模式 (Joint Discussion)**：多 Agent 平等讨论达成一致

实践中常用分层混合架构，兼顾全局可控性和局部灵活性。

**Q: 多 Agent 系统中如何解决无限循环、通信冗余、冲突？**

- **无限循环**：引入状态机管理、设置最大迭代次数、明确终止条件
- **通信冗余**：对 Agent 间传递的内容做摘要，保留核心要点
- **通信冲突**：采用 Pub/Sub 模式、黑板架构、设置仲裁 Agent

### 7. 工具设计与调度

**Q: Agent 的工具注册和调度策略？**

工具注册需包含：名称、功能描述、参数定义（类型、必填性、说明）、返回值格式

调度策略：
- **串行调用**：步骤间有依赖关系
- **并行调用**：多个独立子任务同时执行
- **规划-执行分离**：先生成完整计划，再按计划执行

错误恢复：把失败信息作为 Observation 返回给 LLM，让模型自行决策重试或换策略，避免硬编码恢复逻辑。

**Q: Agent 安全防护怎么做？**

- **输入隔离**：系统指令与用户数据清晰分隔
- **工具权限分级**：只读工具自由调用，写操作需二次审核或人工确认
- **输出过滤**：工具返回数据清洗，防止恶意指令注入（Prompt Injection）
- **行为监控**：异常模式检测和立即阻断

## 第二部分：Go 语言面试题

### 1. GMP 调度模型

**Q: 详细介绍 Go 的 GMP 调度模型？**

GMP 是 Go 运行时调度的核心三元模型：

- **G (Goroutine)**：轻量级协程，初始栈仅 2KB（可动态增长），由 `go` 关键字创建
- **M (Machine)**：操作系统内核线程，负责真正执行计算，数量默认最多 10000 个
- **P (Processor)**：逻辑处理器，管理 Goroutine 队列，数量由 `GOMAXPROCS` 决定（默认等于 CPU 核数）

核心关系：M 必须绑定 P 才能执行 G。每个 P 有本地运行队列（LRQ，最多 256 个 G），还有全局队列（GRQ）。

**Q: 为什么需要 P？不直接让 M 从全局队列取 G？**

早期 Go 1.0 没有 P，所有 G 放在全局队列用大锁保护，多核下锁竞争严重。引入 P 后：
- M 优先从 P 的本地队列无锁取 G，大幅降低竞争
- 每个 P 本地队列独立，形成无锁的快速路径
- 只有本地队列为空时才需要访问全局队列或触发 work-stealing

**Q: 调度策略有哪些？**

1. **队列轮转**：P 周期性调度本地队列的 G，每个 G 分配时间片
2. **饥饿防止**：每调度 61 次检查一次全局队列，防止全局 G 被饿死
3. **工作窃取 (Work-Stealing)**：本地队列为空时，从其他 P 的队列中偷取约一半的 G
4. **Hand-off 机制**：G 执行系统调用阻塞时，M 主动释放 P，其他 M 接管 P 继续工作
5. **抢占式调度 (Go 1.14+)**：基于信号 (SIGURG) 的异步抢占，`sysmon` 发现 G 执行超过 10ms 则强制中断

**Q: sysmon 是什么？做了哪些事？**

`sysmon` 是 Go 运行时的后台监控线程（不绑定 P），负责：
- 监控长时间运行的 G（>10ms），触发抢占
- 监控长时间的系统调用，剥离 P 分配给其他 M
- 触发网络轮询（netpoll）
- 触发强制 GC（超过 2 分钟未 GC）

### 2. Goroutine 与 Channel

**Q: Goroutine 和线程的区别？**

- **栈大小**：Goroutine 初始 2KB（动态增长），线程通常 1-8MB（固定）
- **调度方式**：Goroutine 由 Go 运行时用户态调度，线程由 OS 内核调度
- **切换开销**：Goroutine 切换约几十纳秒，线程切换约微秒级
- **数量限制**：可轻松创建百万级 Goroutine，线程通常数千个就是极限

**Q: Channel 的底层数据结构？**

```go
type hchan struct {
    qcount   uint           // 队列中的数据个数
    dataqsiz uint           // 环形队列大小（缓冲区容量）
    buf      unsafe.Pointer // 指向环形队列的指针
    elemsize uint16         // 元素大小
    closed   uint32         // 是否已关闭
    sendx    uint           // 发送索引
    recvx    uint           // 接收索引
    recvq    waitq          // 等待接收的 goroutine 队列
    sendq    waitq          // 等待发送的 goroutine 队列
    lock     mutex          // 互斥锁
}
```

**Q: 对 nil channel、已关闭 channel 的操作分别会怎样？**

| 操作 | nil channel | 已关闭的 channel | 有数据的 channel |
|------|------------|-----------------|----------------|
| 读取 | 永久阻塞 | 返回零值和 false | 正常读取 |
| 写入 | 永久阻塞 | panic | 正常写入/阻塞 |
| 关闭 | panic | panic | 正常关闭 |

**Q: 无缓冲 channel 和有缓冲 channel 的区别？**

- **无缓冲**：发送和接收必须同时就绪，否则阻塞。天然同步机制。
- **有缓冲**：缓冲区未满时发送不阻塞，未空时接收不阻塞。异步通信。
- 无缓冲容易导致死锁；有缓冲可能引发内存泄漏（goroutine 写入后无人读取）

### 3. Slice 切片

**Q: Slice 和数组的区别？**

- 数组是值类型，长度固定，赋值和传参会复制整个数组
- Slice 是引用类型，动态长度，底层指向一个数组
- Slice 结构：`{pointer, length, capacity}`

**Q: Slice 的扩容机制？**

Go 1.18 版本后的扩容策略：
- 容量 < 256 时：2 倍扩容
- 容量 >= 256 时：按 `(oldcap + 3*256) / 4` 递增，增长更平滑
- 最终容量会按内存对齐规则向上取整

Go 1.18 之前：
- 容量 < 1024 时：2 倍扩容
- 容量 >= 1024 时：1.25 倍扩容

**Q: 切片的陷阱题**

```go
s1 := []int{1, 2, 3, 4, 5}
s2 := s1[1:3]   // s2 = [2, 3], len=2, cap=4
s2 = append(s2, 100)
// s1 变成了 [1, 2, 3, 100, 5]，因为 s2 和 s1 共享底层数组
```

关键点：切片截取后共享底层数组，append 在未触发扩容时会修改原数组。

### 4. Map

**Q: Map 的底层实现？**

- 哈希表 + 链地址法（bucket chain）解决冲突
- 每个 bucket 存 8 个 key-value 对，溢出时创建 overflow bucket
- 扩容条件：负载因子超过 6.5 或溢出 bucket 太多
- 扩容方式：渐进式迁移，每次访问时搬迁少量 bucket

**Q: Map 为什么不是并发安全的？**

- 并发读写会触发 `fatal error: concurrent map read and map write`
- Go 选择不加锁是为了性能（大部分场景不需要并发访问 map）
- 并发安全替代方案：`sync.Map`（读多写少场景）或 `sync.RWMutex` + 普通 map

**Q: sync.Map 的适用场景？**

sync.Map 内部用两个 map（read 和 dirty）实现读写分离：
- 适合读多写少场景：read map 可无锁并发读
- 不适合写多场景：频繁写入时性能可能低于 mutex + map
- 典型场景：缓存、配置读取

### 5. GC 垃圾回收

**Q: Go 的 GC 算法是什么？**

采用三色标记清除法 + 混合写屏障：

三色标记：
- **白色**：未被访问的对象（GC 结束后回收）
- **灰色**：已被访问但其引用的对象未全部扫描
- **黑色**：已被访问且其引用的对象全部扫描完成

四个阶段：
1. 栈扫描（STW，极短）
2. 标记（并发，与应用同时运行）
3. 遍历灰色队列直到为空
4. 清除白色对象（并发）

混合写屏障（Go 1.8+）：结合 Dijkstra 插入屏障和 Yuasa 删除屏障，几乎消除 STW。

**Q: 如何优化 GC 性能？**

- `GOGC` 参数：默认 100（堆增长 100% 触发 GC），设为 50 减小 pause 但增加 GC 频率
- `sync.Pool` 对象复用，减少堆分配
- 减少逃逸：尽量让变量在栈上分配（不取地址、不放 interface{}）
- 预分配 slice/map 容量，减少扩容分配
- 避免大量小对象：合并为结构体或使用 arena

**Q: 常见内存泄漏场景？**

- Goroutine 泄漏：goroutine 因 channel 阻塞永远无法退出
- time.Ticker 未 Stop
- 切片截取后原底层数组无法被 GC（应 copy 出去）
- 全局 map 只增不删
- defer 在循环中导致资源延迟释放

### 6. Context 包

**Q: Context 的作用和核心方法？**

Context 接口提供四个核心方法：
- `Deadline()` - 返回截止时间
- `Done()` - 返回只读 channel，被关闭时表示 Context 被取消
- `Err()` - 返回关闭原因（Canceled 或 DeadlineExceeded）
- `Value(key)` - 返回指定 key 的值（链式递归查找）

三大作用：
- **超时控制**：`WithTimeout` / `WithDeadline`
- **取消信号传播**：父 Context 取消时，所有子 Context 自动取消
- **请求级数据传递**：携带 traceID、userID 等元数据

**Q: Context 取消的传播机制？**

- 父 Context 取消后，所有子 Context 自动取消（级联取消）
- 子 Context 取消不影响父 Context
- 实现原理：父 Context 维护 children map，cancel 时遍历通知所有子 Context

### 7. sync 包

**Q: sync.WaitGroup 的底层实现？**

```go
type WaitGroup struct {
    noCopy noCopy           // 防止复制（go vet 检查）
    state  atomic.Uint64    // 高 32 位：计数器，低 32 位：等待者数量
    sema   uint32           // 信号量，用于阻塞/唤醒
}
```

- `Add(delta)` 原子操作修改计数器
- `Done()` 等价于 `Add(-1)`
- `Wait()` 阻塞直到计数器归零
- 零值可用，无需初始化

**Q: errgroup 和 WaitGroup 的区别？**

errgroup 是 WaitGroup 的增强版，额外支持：
- **错误传播**：任意 goroutine 返回错误时，自动 cancel 所有其他 goroutine
- **Context 集成**：自动管理 context 取消
- **并发限制**：`SetLimit(n)` 限制最大并发 goroutine 数
- 内部用 `sync.Once` 确保只记录第一个错误

**Q: sync.Once 的实现原理？**

```go
type Once struct {
    done atomic.Uint32
    m    Mutex
}
```

- 通过 atomic 读取 done 标志（快速路径，无锁）
- 首次执行时加锁，执行函数后设置 done = 1
- 后续调用直接返回（快速路径）
- 即使 panic 了也标记为 done（Go 1.21 改为 `OnceFunc` 可处理 panic）

---

### 8. Interface 底层

**Q: Interface 的底层表示？**

Go 有两种 interface 底层结构：

空接口 `interface{}`：
```go
type eface struct {
    _type *_type     // 类型信息
    data  unsafe.Pointer  // 数据指针
}
```

非空接口 `interface { Method() }`：
```go
type iface struct {
    tab  *itab           // 类型信息 + 方法表
    data unsafe.Pointer  // 数据指针
}
```

**Q: nil interface 和 interface 包含 nil 指针有什么区别？**

```go
var p *int = nil
var i interface{} = p
fmt.Println(i == nil)  // false!
```

- `i` 的 type 字段不为 nil（是 `*int`），所以 `i != nil`
- 只有 type 和 data 都为 nil 时，interface 才等于 nil
- 这是 Go 面试最经典的陷阱题之一

### 9. make 与 new

**Q: make 和 new 的区别？**

- `make`：仅用于 slice、map、channel，返回初始化后的**变量本身**（非指针）
- `new`：可用于任何类型，返回指向**零值**的**指针**

```go
s := make([]int, 0, 10)  // 返回 []int，已初始化
p := new(int)             // 返回 *int，指向零值 0
```

### 10. defer 机制

**Q: defer 的执行顺序和特性？**

- 多个 defer 按 LIFO（后进先出）执行
- defer 函数的参数在 defer 语句时求值（不是执行时）
- defer 可以修改具名返回值

```go
func f() (result int) {
    defer func() { result++ }()
    return 0    // 实际返回 1
}
```

**Q: defer 的性能开销？**

- Go 1.14+ 引入 open-coded defer，开销接近零（编译时内联）
- 之前版本每个 defer 分配在堆上，有约 30ns 开销
- 循环中的 defer 不会被 open-coded 优化，应避免

### 11. 内存逃逸分析

**Q: 什么是逃逸分析？六大逃逸场景？**

逃逸分析决定变量分配在栈上还是堆上。六大逃逸场景：

1. 返回局部变量的指针
2. 发送指针或带指针的值到 channel
3. 闭包中捕获外部变量
4. 赋值给全局变量或全局 map
5. 赋值给 `interface{}` 类型（编译器无法确定具体类型大小）
6. 超过栈大小的大对象（如超大数组）

使用 `go build -gcflags="-m"` 查看逃逸分析结果。

### 12. 锁与并发安全

**Q: Mutex 和 RWMutex 的区别？**

- `sync.Mutex`：互斥锁，同一时间只有一个 goroutine 可以访问
- `sync.RWMutex`：读写锁，允许多个读者同时读取，写者独占
- 读多写少场景用 RWMutex 性能更好
- Mutex 有两种模式：正常模式和饥饿模式（防止锁饥饿）

**Q: 如何避免死锁？**

- 避免锁嵌套
- 统一加锁顺序（所有 goroutine 按相同顺序获取锁）
- 使用 `context.WithTimeout` 设置锁等待超时
- 用 channel 代替锁（Go 的哲学：不要通过共享内存来通信，而是通过通信来共享内存）

**Q: Go 项目如何做依赖注入？**

## 第三部分：多 Agent 编排与上下文工程

### 1. 多 Agent 并发控制

**Q: 同时开多个 Agent（Cursor、Codex 等）会有什么问题？**

核心问题是资源竞争和冲突：
- **文件冲突**：多个 agent 同时修改同一个文件，产生 merge conflict 甚至互相覆盖
- **信息不同步**：A agent 改了接口签名，B agent 还在用旧签名写调用方，编译不过
- **上下文割裂**：每个 agent 只看到自己的对话上下文，不知道其他 agent 做了什么决策
- **Git 状态混乱**：多个 agent 在同一分支上操作 staging area，commit 历史变得不可预测

**Q: 除了信息不同步，还有什么问题？**

- **任务依赖和顺序**：有些任务有隐式依赖（比如先定义数据模型再写 API），agent 不知道该等谁
- **重复劳动**：两个 agent 可能独立去解决同一个子问题，浪费算力
- **质量标准不一致**：不同 agent session 的 coding style、错误处理策略可能不统一
- **人类认知负担**：你需要记住每个 agent 在做什么、做到哪了，心智开销很大

**Q: 规模到 10-20+ 个 agent 时会出现什么新问题？**

量变引起质变：
- **人成为瓶颈**：一个人根本无法同时跟 20 个 agent 有效互动，审查速度跟不上产出速度
- **冲突爆炸**：N 个 agent 的潜在冲突是 O(N^2) 的组合关系
- **资源争抢**：API rate limit、token 消耗、机器 CPU/内存、网络带宽
- **集成噩梦**：20 个独立完成的模块合到一起，集成测试复杂度远超单模块之和
- **质量失控**：审查不过来就只能放过，技术债务快速积累

### 2. Agent 调度与管理

**Q: 怎么管理多个 agent？**

需要一个调度层（orchestrator）：
- **任务分解 + DAG**：把大任务拆成小任务，建立依赖图（有向无环图），按拓扑序调度
- **隔离策略**：每个 agent 用独立的 git worktree 或 branch，物理隔离文件修改
- **共享状态总线**：用中心化的状态存储（数据库或文件），记录每个 agent 的任务、进度、产出物
- **自动合并 + 冲突检测**：agent 完成后自动尝试合并，冲突时排队或通知人工介入
- **优先级队列**：关键路径上的任务优先调度，非阻塞任务可以并行

**Q: 十几个 agent 同时需要反馈时怎么分配互动？**

本质是中断管理问题：
- **分层处理**：自动化能解决的（lint 错误、简单测试失败）不需要人参与，agent 自己重试
- **批量审查**：设立检查点（checkpoint），每个 agent 完成一个阶段后暂停，人集中审查一批
- **优先级排序**：阻塞其他 agent 的任务优先处理；独立任务可以晚点看
- **异步模式**：让 agent 做到能做的最远，把需要确认的问题排成队列，人按队列逐个处理
- **设定自主权限**：给 agent 明确的决策边界——范围内自己决定，范围外才问人

**Q: 技术上需要实现哪些能力来支撑多 agent 场景？**

| 层 | 能力 |
|---|---|
| 任务管理 | 任务创建、分解、依赖定义、状态流转（pending/running/waiting/done/failed） |
| Agent 生命周期 | 启动、暂停、恢复、终止、超时检测、健康检查 |
| 隔离 | 每个 agent 独立的工作目录/分支、环境变量、资源配额 |
| 通信 | Agent 间消息传递、共享上下文读写、事件广播 |
| 合并 | 自动 merge、冲突检测、回滚能力 |
| 可观测性 | 实时状态面板、日志聚合、token 消耗追踪 |
| 人机交互 | 统一的审批队列、批量操作、紧急中断 |

### 3. Agent 状态监控

**Q: 怎么捕获一个 agent 的状态（waiting/running/done）？**

- **心跳 + 轮询**：agent 定期上报状态（heartbeat），调度器轮询检查
- **事件驱动**：agent 在状态变化时主动推送事件（开始、等待输入、完成、失败）
- **输出流分析**：解析 agent 的 stdout/stderr，通过关键词或结构化输出判断状态（比如 terminal 文件带有 pid、running_for_ms、exit_code 等元数据）
- **文件系统约定**：agent 把状态写入约定路径的文件（如 .status.json），调度器 watch 文件变化

**Q: 像 Codex 这种没有 API 的独立程序，怎么获取状态？**

没有 API 就走外部观测路线：
- **进程监控**：通过 ps、/proc 获取进程是否存活、CPU/内存使用
- **文件系统监控**（inotify / FSEvents）：watch 工作目录，文件变化说明在工作，长时间不变说明可能卡了
- **日志解析**：tail 日志文件，解析输出模式
- **屏幕/终端截取**：最暴力的方式，直接读终端输出内容
- **Wrapper 封装**：用脚本包一层，在启动和退出时打点，中间通过管道拦截输出

**Q: 除了 hook 和 skill 打点，还有什么获取 agent 状态的方法？**

- **操作系统级审计**：macOS EndpointSecurity / Linux auditd，监控进程的文件操作和网络调用
- **Git hooks**：pre-commit、post-commit 自动触发状态上报
- **IDE 插件/扩展**：在 Cursor/VS Code 里装扩展，直接监听编辑器事件
- **网络流量分析**：agent 调用 API 时的网络请求可以被代理拦截（mitmproxy），从请求模式推断状态
- **Sidecar 进程**：跟 agent 一起启动一个轻量伴生进程，专门负责观测和上报

**Q: Agent 卡住了怎么处理？**

分级应对策略：
1. **超时检测**：设定合理的超时阈值，超过就触发告警
2. **自动重试**：先尝试发一个"继续"指令，有时候 agent 只是在等确认
3. **上下文分析**：读 agent 的最后输出，判断是真卡了还是在做耗时操作
4. **强制终止 + 恢复**：kill 进程，从最后一个 checkpoint 恢复，重新分配任务
5. **任务重新路由**：如果某个 agent 反复失败，把任务分配给另一个新的 agent session
6. **降级处理**：实在解不了的子任务标记为 blocked，先跳过，继续其他任务

### 4. 人与 Agent 的分工演进

**Q: 以后人只需要对着调度器做编排就好了？**

调度器会接管大量重复性协调工作，但人不会退化成纯粹的按钮操作员。人的价值转移到：
- **需求定义**：把模糊的业务需求转化成可执行的任务规格
- **架构决策**：决定系统的核心抽象、技术选型、权衡取舍
- **质量把关**：审查关键路径的代码、评估设计合理性
- **异常处理**：agent 搞不定的 edge case 人来兜底
- **复盘和优化**：分析 agent 的工作模式，优化 prompt、skill、工作流

更准确地说，人从"写代码"变成"设计系统、定义规则、监督执行、处理例外"。

**Q: 程序员应该重点发力在哪些领域，避免同质化竞争？**

核心是做 AI 做不好的事：
- **系统设计和架构**：理解业务全貌，做跨系统的设计决策，需要经验和判断力
- **问题定义**：把模糊的"我想要XXX"转化为精确的技术规格，这是最被低估的能力
- **端到端交付**：不只是写代码，而是从需求到部署到运维的全链条负责
- **领域深耕**：在特定领域（金融、医疗、基础设施）建立壁垒，AI 缺乏行业 know-how
- **调试复杂系统**：分布式系统的诡异 bug、性能问题、并发问题仍然需要深厚的基本功
- **构建 AI 基础设施本身**：训练、推理、评估、编排是一个自举的循环
- **人际协作**：跨团队对齐、跟产品经理谈 trade-off、跟客户理解真实需求

核心思路：往上走（架构/决策），往深走（领域专精），往横走（全栈交付）。不要停在"按规格实现功能"这个层面。

### 5. 大规模代码库的上下文管理

**Q: 怎么让大模型从庞大上下文中精确找到需要的数据？**

- **RAG（检索增强生成）**：先用向量检索或关键词搜索找到相关片段，只把这些片段放进 prompt
- **分层索引**：先看文件/模块级摘要再钻入具体文件，类似人类先看目录再翻到具体章节
- **结构化元数据**：给代码和文档打标签（类型、功能、依赖关系），检索时按结构过滤
- **Agent 主动搜索**：让模型自己决定要搜什么，用工具（grep、glob、semantic search）迭代搜索
- **渐进式披露**：先给高层概要，模型需要细节时再加载（CLAUDE.md 的设计思路）
- **KV-cache 友好的 prompt 布局**：稳定上下文（系统 prompt）放前面，变化部分放后面，利用缓存减少重复计算

**Q: RAG 在代码库场景怎么落地？代码是怎么切片的？**

代码切片策略跟普通文本不同，因为代码有结构：

切片粒度：
- **函数/方法级别**：最常见的粒度，每个函数作为一个 chunk
- **类/模块级别**：整个类或文件作为一个 chunk（适合不太大的文件）
- **AST 感知切分**：用 Tree-sitter 等解析器把代码解析成语法树，按语法结构切分，保证每个 chunk 语义完整

索引内容：
- 代码本身的向量嵌入
- 函数签名、docstring、注释
- 文件路径和目录结构
- import/export 依赖关系
- Git blame 信息（谁最近改过）

检索方式：
- **向量语义搜索**：用户描述"登录验证逻辑"，找到语义相关的代码
- **关键词搜索**：精确查函数名、类名、变量名
- **混合检索（Hybrid）**：向量 + 关键词的加权组合，效果最好

**Q: RAG 找错了怎么办？**

- **多路召回**：同时用向量搜索和关键词搜索，取并集，降低漏检率
- **重排序（Reranking）**：第一轮粗召回后用更强的模型做精排，过滤掉不相关的
- **让模型自己判断**：在 prompt 里告诉模型"如果不相关请忽略并尝试自己搜索"
- **迭代搜索（Agentic RAG）**：找到的结果不够好就让 agent 换关键词再搜一次
- **反馈闭环**：通过人工反馈标注优化检索质量
- **设置保险杠**：关键操作前跑测试、lint、类型检查，从结果反推是否用了错误的上下文

**Q: 几百万行代码窗口装不下怎么办？**

核心策略：
- **不装全部只装需要的**：通过检索只提取相关的代码片段
- **分层压缩**：项目级摘要 -> 模块级摘要 -> 具体函数代码，按需展开
- **工具驱动的按需加载**：给模型 grep、glob、read 等工具让它自己决定看哪些文件
- **多轮交互**：一次解决不了就分多次，每次聚焦一个子问题

### 6. AI 编程工具的底层原理（Harness）

**Q: Cursor、Claude Code、Codex 这类工具大概是怎么实现的？**

核心层（Harness）：
1. **代码索引服务**：在后台对整个代码库建索引（AST 解析 + 向量嵌入 + 符号表）
2. **上下文组装器**：根据用户的问题/任务从索引中检索相关代码，拼接成 prompt
3. **工具层**：给模型提供 file read、grep、glob、write、shell 等工具
4. **Agent 循环**：模型输出 -> 解析工具调用 -> 执行工具 -> 结果回填 -> 模型继续
5. **安全沙箱**：限制文件操作范围、网络访问、资源消耗

以 Cursor 为例的具体实现：
- 用 Tree-sitter 做 AST 解析，提取符号表
- 用向量数据库（可能是本地的嵌入索引）做语义搜索
- Tab 补全和 Chat 走不同的 prompt 策略（补全短上下文、Chat 长上下文）
- 通过 LSP（Language Server Protocol）获取类型信息、跳转定义
- diff 展示让用户审查修改

**Q: 先让模型决策再搜索 vs 先本地检索再给模型，各自优缺点？**

方式 A：先把 prompt 给模型，模型决策后再搜索（Agent 模式）

优点：
- 模型理解用户意图后搜索更精准（知道该搜什么）
- 可以多轮迭代搜索逐步缩小范围
- 对模糊需求适应性好（"这个功能哪里有 bug"）

缺点：
- 延迟高，每次搜索都是一轮 API 调用
- token 成本高，多轮交互消耗更多
- 对工具设计依赖大，工具不好用模型搜不到

方式 B：先本地检索把结果塞给模型（RAG 模式）

优点：
- 延迟低，检索在本地完成只有一次 API 调用
- 成本低，一次请求搞定
- 确定性强，检索逻辑可控可测试

缺点：
- 检索质量取决于 query 构造，用户的原始 prompt 可能不是好的检索 query
- 一次检索可能不够，找到的不是最相关的
- 无法动态调整，如果第一次找错了没有纠正机会

实际工程中的最佳实践是混合使用：先做一轮快速的本地检索（方式 B）获取初始上下文，然后让模型在此基础上决定是否需要更多信息（方式 A）。本质是粗筛用 RAG，精排用 Agent。

## 第四部分：Agent 面试新热点（2025-2026 大厂补充）

> 来源：小红书面经、牛客网、腾讯云社区、SegmentFault、GitHub AgentGuide 等，2025-2026 春招高频

### 1. 上下文工程（Context Engineering）

**Q: 什么是上下文工程？和 Prompt Engineering 有什么区别？**

上下文工程是设计、管理和优化提供给 LLM 的全部信息的系统实践，包括：
- 系统 prompt 设计
- 检索增强（RAG）的内容注入
- 对话历史的压缩和摘要
- 工具返回结果的格式化
- 多轮对话的记忆管理

Prompt Engineering 偏向单次提示词的措辞优化，上下文工程更关注整个信息流的架构设计。后者是 Agent 系统工程化的核心能力。

**Q: KV-Cache 在上下文管理中怎么利用？**

- 将稳定不变的内容（系统 prompt、工具描述、项目说明）放在 prompt 最前面
- 变化的内容（用户最新消息、工具返回结果）放在后面
- 这样 KV-Cache 可以缓存前面不变部分的计算结果，后续请求只需计算变化部分
- 实践中可以把首次请求的 P99 延迟从 2s 降到后续请求的 300ms 以内

**Q: "Lost in the Middle" 问题是什么？怎么缓解？**

大模型对 prompt 中间位置的内容注意力最弱，头尾位置注意力最强。缓解方法：
- 把最重要的信息放在 prompt 开头或末尾
- 使用结构化标签（XML tag、markdown heading）划分区域
- 控制注入的文档数量，宁精勿多
- 对长文档做摘要后再注入

### 2. A2A 协议与 Agent 通信

**Q: A2A（Agent-to-Agent）协议是什么？和 MCP 的关系？**

| 维度 | MCP | A2A |
|------|-----|-----|
| 解决的问题 | Agent 与工具/数据源的通信 | Agent 与 Agent 之间的通信 |
| 类比 | USB-C 接口（连设备） | HTTP 协议（连服务） |
| 核心能力 | 工具发现、资源访问、Prompt 模板 | 能力发现（Agent Card）、任务委托、状态同步 |
| 协议基础 | JSON-RPC over stdio/HTTP | HTTP + SSE + JSON-RPC |
| 发起方 | Google (2025.04) | Anthropic (2024.11) |

两者是互补关系：MCP 解决 Agent 与外部世界交互，A2A 解决 Agent 之间协作。

**Q: Agent Card 是什么？**

Agent Card 是 A2A 协议中 Agent 的"名片"，包含：
- Agent 的名称和描述
- 支持的能力列表
- 输入输出格式
- 认证方式
- 端点地址

其他 Agent 通过读取 Agent Card 来发现和调用该 Agent，类似微服务的服务注册与发现。

### 3. Agent Runtime 设计

**Q: 设计一个 Agent Runtime 需要考虑哪些模块？（小红书岗位考点）**

Agent Runtime 是 Agent 的运行时引擎，核心模块：
- **会话状态机**：管理对话的生命周期状态（初始化/运行/等待输入/完成/失败）
- **并发队列**：处理多个用户同时与 Agent 交互
- **超时重试**：工具调用超时自动重试，设定最大重试次数和指数退避
- **权限审计**：记录 Agent 的每一步操作（调了什么工具、传了什么参数、返回什么结果）
- **资源配额**：限制单次任务的 token 消耗、工具调用次数、执行时长

**Q: Agent 的评估平台怎么设计？**

- **自动评估**：LLM-as-Judge，用强模型评估弱模型的输出质量
- **多维度评分**：正确性、完整性、安全性、效率（步数/token）
- **基准测试集**：针对业务场景构建 golden dataset
- **A/B 测试**：同一任务分发给不同 Agent 配置，对比效果
- **回归测试**：每次 prompt/工具变更后自动跑测试集，防止退步

### 4. Agent 成本优化（字节/阿里高频）

**Q: Agent 成本降低 70% 的策略？**

- **分级路由**：简单任务用小模型/快模型，复杂任务才用强模型
- **缓存命中**：对相似问题的 Agent 执行结果做缓存，避免重复推理
- **Prompt 压缩**：移除冗余的上下文、压缩历史对话
- **工具调用精简**：减少不必要的工具调用，合并可并行的调用
- **批处理**：非实时任务攒批调用，提高 GPU 利用率
- **输出约束**：限制模型输出长度，避免冗长回答浪费 token

**Q: P99 延迟从 2s 降至 300ms 的优化方案？**

- **流式输出（SSE/WebSocket）**：首 token 延迟远低于完整响应延迟
- **预取上下文**：在用户输入时就开始检索相关文档
- **KV-Cache 优化**：固定前缀的 prompt 利用缓存
- **模型量化**：INT8/INT4 量化减少推理时间
- **并行工具调用**：无依赖的工具调用同时发起
- **推测解码（Speculative Decoding）**：小模型生成草稿，大模型验证

### 5. 深度研究系统（Deep Research）

**Q: Deep Research 多轮检索的停止机制？**

- **信息饱和度检测**：当新检索的内容与已有内容重复率超过阈值（如 80%），停止检索
- **问题覆盖度**：将原始问题拆解为子问题，当所有子问题都有答案时停止
- **最大轮次限制**：设定上限（如 5 轮），兜底防止无限循环
- **置信度评估**：让模型自评当前答案的置信度，超过阈值则停止
- **成本预算**：token 消耗接近预算上限时强制停止

### 6. Agent 幻觉检测与缓解

**Q: Agent 场景下的幻觉有哪些特殊类型？**

除了传统 LLM 幻觉（编造事实），Agent 还有：
- **工具幻觉**：声称调用了工具但实际没调用，或编造工具返回结果
- **能力幻觉**：声称自己能做某事但实际没有对应工具
- **状态幻觉**：对当前任务状态的错误认知（以为完成了但实际没完成）

缓解策略：
- 强制要求工具调用的结构化输出，便于校验
- 工具返回结果直接注入上下文，不让模型"复述"
- 在关键节点加入事实核查步骤
- 对 Agent 的自我评估持怀疑态度，用外部验证替代

### 2. 金融系统幂等与一致性

**Q: 支付回调重复到达怎么处理？（高频场景题）**

错误做法：先查状态再更新（有并发窗口）

```go
// 错误：存在并发问题
order := db.FindByID(id)
if order.Status == "unpaid" {
    order.Status = "paid"
    db.Save(order)
}
```

正确做法：条件更新（幂等）

```go
// 正确：利用数据库的原子性
result := db.Model(&Order{}).
    Where("id = ? AND status = ?", id, "unpaid").
    Update("status", "paid")
if result.RowsAffected == 0 {
    // 已经支付过了，幂等返回成功
}
```

核心原则：用数据库条件更新替代"先查再改"，天然幂等。

**Q: 状态机设计的要点？**

- 核心状态和后置动作解耦：状态变更是同步的，后续通知/清算是异步的
- 状态流转只允许合法路径（如 unpaid -> paid，不允许 paid -> unpaid）
- 用 Go 的 channel 或 MQ 做事件驱动，状态变更后发事件，消费者异步处理后置逻辑
- 关键路径上做消息表 + MQ 异步补偿，保证最终一致性

### 3. 用户中心高并发

**Q: 用户中心的高并发挑战和方案？**

- **读多写少**：用户信息查询远多于修改，适合多级缓存（本地缓存 -> Redis -> DB）
- **缓存一致性**：写操作时先更新 DB 再删缓存（Cache-Aside），配合消息队列做延迟双删
- **热点用户**：大 V 用户的 profile 被频繁访问，用本地缓存 + 短 TTL 缓解 Redis 热点
- **登录态管理**：JWT + Redis session，JWT 无状态减少 Redis 查询，关键操作再查 Redis 验证

**Q: 批量处理 10 万用户数据时怎么做？**

"限流 + 容错 + 收敛"三步走：

```go
func batchProcess(userIDs []int64) error {
    g, ctx := errgroup.WithContext(context.Background())
    g.SetLimit(50) // 限制最大并发
    
    for _, id := range userIDs {
        id := id // Go 1.21 及之前需要创建副本
        g.Go(func() error {
            select {
            case <-ctx.Done():
                return ctx.Err()
            default:
                return processUser(id)
            }
        })
    }
    return g.Wait()
}
```

关键点：
- errgroup.SetLimit 控制并发数，防止打爆下游
- context 传播取消信号
- 单个失败不影响其他（或用 context 取消全部，取决于业务需求）

## 第六部分：Go 高频代码陷阱题（2025-2026 新增）

### 1. range 循环变量复用

**Q: 以下代码输出什么？为什么？**

```go
stus := []student{{"zhou", 24}, {"li", 23}}
m := make(map[string]*student)
for _, stu := range stus {
    m[stu.Name] = &stu
}
// m["zhou"] 和 m["li"] 都指向 {"li", 23}
```

原因：Go 1.21 及之前，range 的循环变量 stu 是复用的同一个栈变量，每次迭代只更新其值，地址不变。所有 `&stu` 都指向同一个地址，最终存储的是最后一次迭代的值。

正确写法：
```go
// 方式1：取切片元素地址
for i := range stus {
    m[stus[i].Name] = &stus[i]
}
// 方式2：创建副本
for _, stu := range stus {
    s := stu
    m[s.Name] = &s
}
```

注意：Go 1.22 起每次迭代创建独立变量，此问题已修复，但面试仍会考。

### 2. goroutine 闭包陷阱

**Q: 以下代码的输出是什么？**

```go
for i := 0; i < 5; i++ {
    go func() {
        fmt.Println(i)
    }()
}
time.Sleep(time.Second)
```

Go 1.21 及之前：大概率输出 5 个 `5`，因为闭包捕获的是变量 i 的地址，goroutine 执行时循环已结束，i = 5。

正确写法：
```go
// 方式1：传参
for i := 0; i < 5; i++ {
    go func(n int) {
        fmt.Println(n)
    }(i)
}
// 方式2：Go 1.22+ 自动修复
```

### 3. 高并发场景三板斧

**Q: goroutine 不能无限制创建，生产环境怎么管理？**

三个维度：限流 + 超时 + 兜底

```go
// 限流：用 channel 做信号量
sem := make(chan struct{}, 100) // 最多100个并发
for _, task := range tasks {
    sem <- struct{}{} // 获取令牌
    go func(t Task) {
        defer func() { <-sem }() // 释放令牌
        
        // 超时：用 context 控制生命周期
        ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
        defer cancel()
        
        // 兜底：recover 防止单个 goroutine panic 导致全局崩溃
        defer func() {
            if r := recover(); r != nil {
                log.Printf("recovered: %v", r)
            }
        }()
        
        process(ctx, t)
    }(task)
}
```

## 第七部分：微服务与 RAG 实战面试话术

### 1. 微服务架构选型话术

**Q: 为什么选微服务？**

面试高分回答模板（STAR 法则）：

> 在我们的项目中，简历解析、AI 问答、知识库管理这些模块功能独立且资源需求不同（解析耗 CPU，问答耗 GPU 内存），这是拆服务的核心原因。之前用单体架构编译一次要 45 分钟，任何小改动都得全量重编。拆成微服务后用 Docker Compose 管理，每个服务独立编译部署，开发效率提升 3 倍以上。

不回避缺点：分布式事务、链路追踪、服务间调用稳定性（超时/熔断/降级）这些运维复杂度确实增加了。

**Q: SSE vs WebSocket 怎么选？**

| 场景 | 选择 | 原因 |
|------|------|------|
| AI 回答流式推送 | SSE | 单向推送，基于 HTTP，Go 实现不到 50 行 |
| 实时聊天 | WebSocket | 需要双向通信 |
| 股票行情推送 | SSE 或 WebSocket | 看是否需要客户端主动发消息 |

SSE 核心优势：基于标准 HTTP，自带重连机制，实现简单，Go 中只需设置 `Content-Type: text/event-stream`。

### 2. RAG 工程实战话术

**Q: 向量数据库为什么选 PgVector 不选 Milvus？**

面试高分回答：

> 三个原因：第一，项目处于快速迭代阶段，数据量千万级以下，PgVector 性能足够；第二，PgVector 作为 PostgreSQL 扩展无缝集成，一套 SQL 搞定关联查询和向量检索，开发效率高；第三，继承了 PostgreSQL 的 ACID 事务特性，业务数据和向量数据可以在一个事务里保证一致性。架构上做了隔离，未来数据量暴涨可以平滑迁移到 Milvus。

**Q: RAG 的质量怎么保证？**

- **检索阶段**：混合检索（向量 + BM25）+ Rerank 精排
- **生成阶段**：在 prompt 中明确要求"仅基于给定上下文回答，如果上下文不足则说明"
- **验证阶段**：对关键事实做引用标注，让用户可追溯验证
- **量化指标**：用 Faithfulness（忠实度）、Relevancy（相关性）、Answer Correctness（正确性）三维评估
